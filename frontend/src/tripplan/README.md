# Trip planning screen

`src/app/trip-plan.tsx` exposes `TripPlanningScreen` as the `/trip-plan` route. The map menu links to it. The screen is protected by the existing `useSession` hook and redirects signed-out visitors to `/login`.

The page keeps all search inputs in local state. Both city fields use `GET /api/trip-plans/cities?city=...` only when the user presses **Search**. Selecting a GeoNames suggestion preserves its `lookupName` and `countryCode`; selecting a departure city then calls `GET /api/trip-plans/cities/{city}/airports?countryCode=...`. Airports without IATA codes are displayed but cannot be selected for flight search. A city or form change hides previous flight results, and request counters ignore stale responses that arrive after a newer selection. The page waits for an active flight search to finish before allowing another, which avoids overlapping paid provider searches.

Flight search calls `POST /api/trip-plans/flight-searches` with the selected origin IATA code, selected destination city/country, total EUR budget, local departure datetime interval, staying nights, and ticket option. A cross-platform calendar supplies `YYYY-MM-DD` dates and a numeric time field supplies 24-hour `HH:MM` times; the page combines them into local ISO datetime strings without a timezone suffix. The page validates their format and ordering; the backend remains responsible for its configured maximum date range and city/airport validity. Flight searches can be slow, so the feature API client uses a 90-second timeout rather than the sign-in client's shorter timeout.

The backend response may contain zero to its configured limit of itineraries (three by default). Each ticket shows its total price, all outbound and return segments, and the available Google Flights search links. Selecting a card expands its details. For two one-way tickets, the first link is outbound and the second is return. Links are opened only when they use HTTPS on `www.google.com` under `/travel/flights`. They may lead to a search page instead of the exact displayed offer, and availability may change.

Accommodation search is available on the same page, even when no flight has been selected. It reuses the selected destination city/country and staying nights, but has its own total EUR budget. Selecting a flight fills the check-in date from the **final outbound segment's arrival** date; the user can choose another date in the calendar. The page calls `POST /api/trip-plans/accommodation-searches` only after **Find stays** is pressed, clears old stay offers when search inputs change, and blocks overlapping accommodation requests. Offer cards show the full-stay tax-inclusive price for one adult, stay dates, property type, description, address, rating and review count, amenities, room names, booking options with source-specific prices, and an optional property website. Booking links and property websites are labeled separately; prices can change after the search.

The final card lets a signed-in user save the preset through `POST /api/trip-plans`. It requires a title and accepts an optional description. It sends the selected departure city/country and origin airport, destination city/country, local departure interval, staying nights, ticket option, and separate EUR budgets. It does not include the accommodation check-in date or any flight/hotel offer, because those are specific to a search. A successful save shows a confirmation and disables another save until an input in the saved preset changes. The backend has create and view only, so saving changed inputs creates a new plan; the button labels this explicitly. Edits during a pending save do not show a stale success confirmation.

`api/tripPlanning.ts` owns the frontend DTO types and HTTP requests. It obtains the current app JWT through the existing session module and never persists the token or search data locally.
