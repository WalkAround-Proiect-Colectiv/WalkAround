# Trip planning screen

The travel selector offers Plane, Bus, and Train. Plane uses the selected origin airport; Bus and Train send both selected GeoNames cities and country codes to their respective `/api/trip-plans/bus-searches` and `/api/trip-plans/train-searches` endpoints. All three modes use a total EUR budget, local departure interval, staying nights, ticket option, and a manually entered count of 1 to 9 adults. The airport picker appears only for Plane; the saved-plan form works for every transport mode. Changing transport or adult count clears stale ticket results and the saved confirmation; selecting an itinerary suggests accommodation check-in from its outbound arrival date. A group can save alternative search presets, identify one as current, and reopen a preset with its search fields restored. Reopening does not fetch live tickets or stays.

The top of the planner links to group creation and `/trip-groups`. The creation page accepts a name, optional description, and optional JPEG/PNG photo, then links to the new group. The group page lists memberships and lets an admin create, share, and revoke one-use invitation links. Opening a link previews the group and allows a signed-in user to join; a signed-out user returns to the invite after sign-in. Group members can open the same planner from their group view, save group-owned search presets, and see the current group plan. The first saved plan becomes current; admins can select a different current plan. The floating message button opens the group's dedicated chat view.

Group chat uses HTTP for authenticated, idempotent message saves and sequence-cursor history. It receives live messages through the conversation-scoped WebSocket. On connection or reconnect, it waits for `SUBSCRIBED` before requesting history or catch-up, then merges by message ID. A failed send retains its UUID for the retry so it cannot create a second message.

When a group plan is saved, connected members receive an app-wide notification through the existing authenticated WebSocket. **View plan** opens the saved preset and refreshes the group's plan list. Disconnected members can still find the plan in the group view; these group notifications do not have a missed-notification inbox.

Group admins can open `/trip-group-edit` from the group page to change the name, description, and photo. The edit form can keep, replace, or remove the existing photo, and saves through a protected backend `PUT` request.

Group photos appear in the group list, detail, creation confirmation, edit form, and invitation preview. The invite preview uses its active invitation token for the photo because the invitee is not a member yet; other views use the member-protected photo endpoint.

Bus cards and Omio-sourced train cards open Omio searches prefilled with the journey's cities and dates. Round trips use one search with a return date; two one-way tickets use separate outbound and return searches. The user must select the offer again on Omio because the links do not identify an exact fare.

For Romanian city pairs, a Two one-way train request can also return Bilo offers when the backend has a Bilo API key. Round trip requests return Omio offers only. Cards identify their source. Bilo pairs use two one-way tickets, show the published original RON fare and an approximate EUR total, and open Bilo's published ticket/search links when available. The backend applies the shared EUR budget after conversion; final fares and seat availability must be checked with the operator.

`src/app/trip-plan.tsx` exposes `TripPlanningScreen` as the `/trip-plan` route. The map menu links to it. The screen is protected by the existing `useSession` hook and redirects signed-out visitors to `/login`.

The page keeps all search inputs in local state. Both city fields use `GET /api/trip-plans/cities?city=...` only when the user presses **Search**. Selecting a GeoNames suggestion preserves its `lookupName` and `countryCode`; selecting a departure city then calls `GET /api/trip-plans/cities/{city}/airports?countryCode=...`. The airport list appears in Plane mode and shows city matches first and nearby airports afterward. Airports without IATA codes cannot be selected for flight search. A city or form change hides previous ticket results, and request counters ignore stale responses. The page waits for an active transport search to finish before allowing another, which avoids overlapping paid provider searches.

Flight search calls `POST /api/trip-plans/flight-searches` with the selected origin IATA code, selected destination city/country, total EUR budget, local departure datetime interval, staying nights, and ticket option. A cross-platform calendar supplies `YYYY-MM-DD` dates and a numeric time field supplies 24-hour `HH:MM` times; the page combines them into local ISO datetime strings without a timezone suffix. The page validates their format and ordering; the backend remains responsible for its configured maximum date range and city/airport validity. Flight searches can be slow, so the feature API client uses a 90-second timeout rather than the sign-in client's shorter timeout.

The backend response may contain zero to its configured limit of itineraries (three by default). Each ticket shows its total price, all outbound and return segments, and the available Google Flights search links. Selecting a card expands its details. For two one-way tickets, the first link is outbound and the second is return. Links are opened only when they use HTTPS on `www.google.com` under `/travel/flights`. They may lead to a search page instead of the exact displayed offer, and availability may change.

Accommodation search is available on the same page, even when no ticket has been selected. It reuses the selected destination city/country, staying nights, and adult count, but has its own total EUR budget. Selecting a travel option fills the check-in date from its final outbound arrival date; the user can choose another date in the calendar. The page calls `POST /api/trip-plans/accommodation-searches` only after **Find stays** is pressed, clears old stay offers when search inputs change, and blocks overlapping accommodation requests. Offer cards show the full-stay tax-inclusive price for the selected adults, stay dates, property type, description, address, rating and review count, amenities, room names, booking options with source-specific prices, and an optional property website. Booking links and property websites are labeled separately; prices can change after the search.

The final card lets a signed-in user save the preset through `POST /api/trip-plans` for personal planning or `POST /api/trip-plan-groups/{id}/plans` from a group. It requires a title and accepts an optional description. It sends the transport mode, selected departure and destination city/country pairs, local departure interval, staying nights, adult count, ticket option, and separate total EUR transport and accommodation budgets. Plane adds the selected origin airport; Bus and Train send no airport. It does not include the accommodation check-in date or any provider offer. A successful save shows a confirmation and disables another save until an input in the saved preset changes. Saving changed inputs creates a new preset; edits during a pending save do not show a stale success confirmation.

`api/tripPlanning.ts` owns the frontend DTO types and HTTP requests. It obtains the current app JWT through the existing session module and never persists the token or search data locally.

Choosing a destination also loads the first tourist-attractions page into the places section at the bottom of the page. The section has tourist-attraction, restaurant, museum, and coffee-shop categories; the latter three load when their tab is selected. Each category keeps its own pages for the selected city. Place cards show optional details and safe external map and website links. Further pages load only through **Load more places**; errors have an explicit retry. Requests do not run on text input or re-render.

A country hotlines card appears immediately after the destination choice, before the live safety card. It loads locally imported contacts for the selected country's code, keeps general emergency numbers visible, and expands to categorized support services. The local lookup makes no paid provider call. A destination change clears the previous country's contacts and ignores its late response.

A separate safety card appears after the hotlines card. The user checks safety explicitly, so selecting a city does not spend Travel Risk API requests. The backend validates the city with GeoNames, then retrieves country advisories and reports near the city. The card separates these geographic scopes, shows source links and the check time, and clears its data when the destination changes. Safety information is not saved with the trip preset.

An optional destination news card follows places at the bottom of the page. It makes one backend news request only after the user presses its button, preserves article links and metadata, and clears its results when the destination changes. The backend keeps the Currents API key private.

The destination weather widget sits after the destination selector and before the hotlines and safety cards. Its button requests the next 14 local forecast days from the backend's Open-Meteo integration; selecting a city alone makes no weather call. It highlights known check-in nights within the forecast window and explains when a future trip has no available forecast yet.

With a check-in date and stay length, a separate button requests historical weather for the entire stay in each of the three most recent completed comparable years. The comparison is optional and available even when the forecast covers every trip day. Changing the city or stay clears historical results.
