# Trip planning page

`TripPlanningScreen` is a single-page, mobile-first onboarding flow. Users explicitly search for and select GeoNames city suggestions, choose a local departure airport, enter budget, departure dates and times, nights, and ticket style, then inspect selectable flight cards on the same page. They can then search accommodations with the selected destination, staying nights, a separate accommodation budget, and a check-in date from the chosen flight's final outbound arrival or the calendar. Dates are chosen through `components/CalendarPicker.tsx`; budget, night count, and time fields strip nonnumeric input. Changing an input hides outdated offers. Flight cards expand to show every outbound and return segment and safe Google Flights links; accommodation cards show all returned property details, available booking options, and the separate property website when present.

The destination safety card sits below weather and country hotlines, before budgets and ticket search. A selected destination enables **Check safety**. This explicit action makes the backend request; typing and rendering do not consume Travel Risk API requests. The card shows country-wide advisory levels and agency sources separately from geolocated alerts and recent conflicts near the validated city. It displays the check time, configured radius, any partial-data flags, and the limitation that unlocated reports are excluded. **Refresh safety** makes a new request. Changing destinations clears old safety data and ignores an in-flight result for the previous city. An empty nearby list is described as an absence in the retrieved data, not proof of safety.

The country hotlines card appears between the weather widget and the live safety card, so emergency contacts are available before travel-search inputs. Selecting a destination loads its country hotlines from the local database automatically. General emergency numbers stay visible; the categorized service list expands on demand so the long list does not bury the trip form. Each hotline shows its available voice, SMS, text, or short-code numbers and relevant service and verification details. Changing destinations clears the previous country's data and ignores its in-flight response. A failed lookup offers a retry action. This lookup makes no external provider request.

The weather widget appears directly below the destination city choice. It fetches a destination-local 14-day forecast only when **Show 14-day forecast** or **Refresh forecast** is pressed. The user can inspect each daily condition and temperature; check-in date and staying nights mark the booked days within the available window. Later or partly covered stays receive an availability message. Changing destinations clears the forecast and ignores a late response. It does not claim to forecast a trip more than 14 days ahead.

Destination news sits at the bottom of the page after places, since it is useful context rather than a core trip input. Selecting a destination enables **See destination news** but does not request news automatically. The action validates the city through the backend and makes one Currents Search request for an English-language page. The card shows five articles initially and can expand to the rest without another request. **Refresh news** makes one new request. Changing destinations clears articles and ignores late responses. The safety, weather, and news cards use distinct destination-scoped React keys so their local expansion states reset without key collisions before a city is selected. The provider's country filter selects publisher sources; an article mentioning the city may not describe events in it.

The final card saves the current search preset with a required title and optional description. The user can save without running either search; the selected provider offers and accommodation check-in date are not stored. Saving validates the form, blocks duplicate taps, shows an error or success on the same page, and resets the success state when a stored input changes. Saving again after an edit creates another plan because the backend currently exposes creation rather than editing. The page is available at `/trip-plan` and requires a signed-in session.

The places section appears below the save card. Selecting a destination from autocomplete starts page 0 of tourist attractions, independent of flight and accommodation searches. Restaurants, Museums, and Coffee shops each load page 0 only when the user opens that category. The user presses **Load more places** to request `nextPage`; pages append to the current category, and repeated Maps URLs are hidden. Typing, changing other inputs, and rendering the page do not start place requests. `PLACE_CATEGORIES` lists the available categories, while the API client sends the typed category to a shared request method. Results are kept per category for the selected city, so switching back to a loaded category uses its existing results without another SerpApi search. Changing the destination clears all categories and ignores in-flight responses for the previous city. A failed first or later page shows an explicit retry action without discarding already loaded places. There are no automatic retries that would consume extra SerpApi searches. Recommendations may include nearby places outside the selected city's limits.
The trip page owns historical weather loading and clears stale comparisons on destination, check-in date, or night-count changes. In-flight results are ignored after these inputs change. The historical button is independent of forecast loading and remains available for trips within the 14-day forecast.
