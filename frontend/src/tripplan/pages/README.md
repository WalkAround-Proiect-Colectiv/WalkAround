# Trip planning page

`TripPlanningScreen` is a single-page, mobile-first flow. Users explicitly search for and select GeoNames cities, then choose Plane, Bus, or Train. Plane requires a selected departure airport; Bus and Train use the two selected cities and their country codes. All modes share a total EUR budget, local departure interval, staying nights, ticket style, and manually entered adult count. Changing a search input hides outdated results. Dates use `components/CalendarPicker.tsx`; budget, night count, adult count, and time fields strip nonnumeric input.

The group card near the top links to `CreateTripGroupScreen` and `TripGroupsScreen`. Creation uses the signed-in session, selects an optional image with Expo Image Picker, and sends one multipart request. The group page lists the current user's groups and, for admins, creates, shares, lists, and revokes one-use invitation links. `TripGroupInviteScreen` reads a link token from the URL fragment, preserves it through login, previews the group, and joins on explicit confirmation.

`GroupChatScreen` opens from the floating message button on the group view. It displays sequenced history, older-page loading, live updates, and a message composer. A send failure leaves the draft message visible with Retry and Discard actions; Retry reuses the original client UUID. The screen obtains a short-lived socket ticket, waits for the `SUBSCRIBED` acknowledgement, then fetches history or missed messages. While connected, it also catches up by sequence every three seconds so a missed socket event appears without reopening the page. WebSocket events and HTTP responses merge by message ID, so a Kafka replay or HTTP retry remains one visible message. The chat view stays within `/trip-groups?groupId=...&tab=chat`.

The chat header keeps the group photo, name, and connection state visible above the conversation. The message area groups entries by local day, uses the app's blue and purple palette, and retains sender names and timestamps. The composer stays at the bottom with the retry controls above it.

The composer has an emoji button that opens `EmojiPicker` above it. The picker includes all bundled Unicode Emoji 18.0 entries, with category tabs and name search. Choosing an emoji inserts it at the saved cursor position while respecting the 2,000-character message limit. The native keyboard can still be used for emoji entry. Closing or sending a message hides the palette.

The poll button opens a compact question and choice form above the composer. Posting a poll uses the same idempotent message POST as text. Poll cards remain at their original chat position while votes, changed choices, and close actions update their counts, selection, and status. The screen subscribes to the socket before taking an event cursor and loading messages; later event pages and WebSocket snapshots merge by message ID and poll revision. The event cursor, rather than the chat message cursor, preserves poll updates across reconnects.

Admins can open `EditTripGroupScreen` from their group page. It loads the current details, validates edited text and optional JPEG/PNG image, and lets the admin retain, replace, or remove the photo. The backend enforces the role and writes all changes in one transaction. Saving returns to the group page.

Where a group is displayed, its photo appears when available: the group list, detail heading, creation confirmation, edit form, and invitation preview. A rounded group icon appears when there is no photo or a protected picture request fails.

The group view includes a **Plan a group trip** action that opens the existing planner with the group context. It retains all destination, transport, accommodation, safety, weather, and place features. Users enter 1 to 9 adults manually; the same count applies to all travel and stay requests and budgets cover the full party. Saving from that view creates a group-owned preset. The first preset is current; later ones are alternatives. Group members see and can refresh the current plan, while admins can make an alternative current. The group view shows the current plan's route, departure period, budgets, nights, and adult count so members know which preset is being discussed. **Open current preset** and **Open preset** restore the saved fields, including adult count and origin airport; reopening makes no ticket or stay search until the user requests one. A missing airport in the current lookup must be selected again. The places section offers a manual load action for reopened presets so they do not spend a SerpApi search on entry.

The app-wide notification banner links new group-plan messages to `/trip-groups?groupId=...&tab=plan&planId=...`. The group screen reloads the plan list when this plan ID changes, so opening a notification for a newly created preset works even if the member was already viewing that group.

While a group page is open, it subscribes to `groupPlanNotifications.ts`. A new-plan message for that group reloads the saved plans immediately, updating both the current-plan summary and alternatives without a tap or page reload. Request IDs prevent an older in-flight plan-list response from replacing the newer list. Other groups' messages do not trigger requests.

Flight cards expand to show outbound and return segments and safe Google Flights links. Bus and train cards show both journey departures in their collapsed state; expanded cards show stations, operators, legs, transfers, optional availability, and prefilled Omio searches. Selecting any itinerary suggests accommodation check-in from the final outbound arrival date; the user can also choose a date in the calendar. Accommodation offers remain on the same page with a separate full-stay EUR budget. The save form appears for Plane, Bus, and Train, and stores the selected transport mode.

Domestic Romanian train results can contain Omio and Bilo offers together when the user selects Two one-way. Round trip shows Omio round-trip fares only. Bilo cards display their source, original fare, approximate converted EUR total, and the available published links.

The departure airport list labels each option as a city or nearby airport and shows the straight-line distance from the selected city's center. Nearby airports are selectable when they have an IATA code; the label does not claim the airport officially serves that city.

The destination safety card sits below weather and country hotlines, before budgets and ticket search. A selected destination enables **Check safety**. This explicit action makes the backend request; typing and rendering do not consume Travel Risk API requests. The card shows country-wide advisory levels and agency sources separately from geolocated alerts and recent conflicts near the validated city. It displays the check time, configured radius, any partial-data flags, and the limitation that unlocated reports are excluded. **Refresh safety** makes a new request. Changing destinations clears old safety data and ignores an in-flight result for the previous city. An empty nearby list is described as an absence in the retrieved data, not proof of safety.

The country hotlines card appears between the weather widget and the live safety card, so emergency contacts are available before travel-search inputs. Selecting a destination loads its country hotlines from the local database automatically. General emergency numbers stay visible; the categorized service list expands on demand so the long list does not bury the trip form. Each hotline shows its available voice, SMS, text, or short-code numbers and relevant service and verification details. Changing destinations clears the previous country's data and ignores its in-flight response. A failed lookup offers a retry action. This lookup makes no external provider request.

The weather widget appears directly below the destination city choice. It fetches a destination-local 14-day forecast only when **Show 14-day forecast** or **Refresh forecast** is pressed. The user can inspect each daily condition and temperature; check-in date and staying nights mark the booked days within the available window. Later or partly covered stays receive an availability message. Changing destinations clears the forecast and ignores a late response. It does not claim to forecast a trip more than 14 days ahead.

Destination news sits at the bottom of the page after places, since it is useful context rather than a core trip input. Selecting a destination enables **See destination news** but does not request news automatically. The action validates the city through the backend and makes one Currents Search request for an English-language page. The card shows five articles initially and can expand to the rest without another request. **Refresh news** makes one new request. Changing destinations clears articles and ignores late responses. The safety, weather, and news cards use distinct destination-scoped React keys so their local expansion states reset without key collisions before a city is selected. The provider's country filter selects publisher sources; an article mentioning the city may not describe events in it.

The final card saves the current search preset with a required title and optional description. The user can save without running either search; the selected provider offers and accommodation check-in date are not stored. It saves personally on `/trip-plan` and to a group when opened from `/trip-groups` with a group context. Saving validates the form, blocks duplicate taps, shows an error or success on the same page, and resets the success state when a stored input changes. Saving again after an edit creates another plan because the backend currently exposes creation rather than editing. Both routes require a signed-in session.

The places section appears below the save card. Selecting a destination from autocomplete starts page 0 of tourist attractions, independent of flight and accommodation searches. Restaurants, Museums, and Coffee shops each load page 0 only when the user opens that category. The user presses **Load more places** to request `nextPage`; pages append to the current category, and repeated Maps URLs are hidden. Typing, changing other inputs, and rendering the page do not start place requests. `PLACE_CATEGORIES` lists the available categories, while the API client sends the typed category to a shared request method. Results are kept per category for the selected city, so switching back to a loaded category uses its existing results without another SerpApi search. Changing the destination clears all categories and ignores in-flight responses for the previous city. A failed first or later page shows an explicit retry action without discarding already loaded places. There are no automatic retries that would consume extra SerpApi searches. Recommendations may include nearby places outside the selected city's limits.
The trip page owns historical weather loading and clears stale comparisons on destination, check-in date, or night-count changes. In-flight results are ignored after these inputs change. The historical button is independent of forecast loading and remains available for trips within the 14-day forecast.
