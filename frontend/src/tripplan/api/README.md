# Trip planning API client

`groupChat.ts` owns the authenticated group-chat HTTP calls: send with a stable client UUID, read message pages using sequence cursors, and request the short-lived WebSocket ticket. The chat screen uses the existing `EXPO_PUBLIC_WS_URL` for live delivery. The token is kept in memory and messages are never written through the socket.

`tripPlanning.ts` defines the request and response types and calls trip-planning endpoints for city autocomplete, city airports, flight, bus, and train search, accommodation search, saved-plan creation, four place categories, destination safety, country hotlines, destination news, and weather. `searchBuses` and `searchTrains` post their city-based presets to `/api/trip-plans/bus-searches` and `/api/trip-plans/train-searches` through the authenticated `send` helper. Their response types contain a combined fare, outbound and return journeys, legs, and optional transfer stops. Scrappa requests and its key stay on the backend.

`tripGroups.ts` submits an authenticated multipart `POST /api/trip-plan-groups` with a required name and optional description and image. It uses a browser `File` on web and a local URI part in React Native. The backend returns the new group ID, the creator's `ADMIN` member role, and an optional member-protected picture URL. The client sends no owner ID or role. The same client lists joined groups, creates/lists/revokes admin invitations, and previews/accepts an invitation with its token in a JSON body. Creation returns the raw token once; later listings contain metadata only.

`updateTripGroup` sends a multipart `PUT /api/trip-plan-groups/{id}` with the edited name and description. It can send a new image or `removePicture=true`; omitting both keeps the current image. The backend checks admin membership, so hiding the edit action in the frontend is only a usability choice.

The edit page loads an existing photo through the authenticated picture request. On web, it displays a temporary object URL and revokes that URL when the page unloads; native uses an image request with the current bearer header.

`getTripGroupPicture` retrieves a member-protected JPEG. `getGroupInvitePicture` sends a valid invitation token in a JSON body to retrieve the photo before membership exists. `TripGroupInvitePreview.pictureAvailable` prevents a photo request for groups without a picture. Tokens never appear in picture URLs.

Transport and accommodation request types include `adults` from 1 to 9; the backend sends that count to SerpApi, Scrappa Omio, or Bilo. Budgets remain totals for the selected people. `saveTripPlan` posts to the personal endpoint normally and to the group-owned endpoint when given a group ID. `tripGroups.ts` lists group plans and lets an admin mark one current. The response includes adult count, group ID, and current status; no live ticket or stay offer is saved.

`groupPlanNotifications.ts` is a small in-memory subscription channel for authenticated `GROUP_PLAN_SAVED` WebSocket messages. The app-wide notification banner publishes the group and plan IDs to it. A mounted group page subscribes and reloads its plan list only when the message belongs to that group; opening the page later uses the normal initial list request. The channel does not store messages or open another WebSocket.

`pendingGroupInvite.ts` keeps a token temporarily while an invitee signs in, using web session storage or native SecureStore. Invite links put the token after `#` so web requests do not send it to the hosting server. The invite screen strips the web fragment once saved. The login screen checks pending invites after authentication and routes to `/trip-group-invite`; it clears the pending token after successful acceptance or when the user dismisses it. Neither the raw token nor its hash is logged.

`TrainItinerary` also identifies Omio or Bilo as its source. Bilo responses can include original RON fare, estimated-fare status, and published outbound/return links; their EUR total is an approximation using a Frankfurter rate fetched by the backend for that search. The Bilo key stays on the backend.

`getPlaceRecommendations` accepts the selected GeoNames destination, a typed category (`attractions`, `restaurants`, `museums`, or `coffee-shops`), and a page number. It calls `GET /api/trip-plans/cities/{city}/{category}?countryCode=...&page=...` and returns `PlaceRecommendationPage` with `items` and nullable `nextPage`. `getDestinationSafety` calls `GET /api/trip-plans/cities/{city}/safety?countryCode=...` only when the user requests it. Accommodation search uses the selected destination, first booked night, stay length, and a separate full-stay EUR budget. Saved-plan creation sends the selected transport mode and its preset, title, and optional description, but excludes check-in date and provider offers. Plane includes an airport; Bus and Train omit it. The client URL-encodes city names and country codes, sends the current application JWT, applies a 90-second request timeout, and turns backend `ProblemDetail.detail` into a page error. It does not call external providers or store the token locally.

Optional bus journey fields include a validated operator logo URL, stop city/country, tickets left, and split-ticket status. Legs include duration and time zones; `BusTransfer` includes the leg after which a transfer occurs and its wait duration. The UI hides absent values.

`BusTransfer.fromStop` and `toStop` contain the position ID and, when resolved by the backend, a station name, city, and country code. The browser makes no direct Places requests.

`getCityAirports` returns city matches followed by nearby airports. Each airport includes `matchType` and straight-line `distanceKm`; the backend validates the city through GeoNames and calculates nearby matches from local airport coordinates. Only airports with IATA codes can be selected for flight search.

`getCountryHotlines` calls `GET /api/trip-plans/countries/{countryCode}/hotlines` after a destination is selected. The country code comes from the selected GeoNames suggestion; the backend reads the local emergency-number database. The response groups numbers by hotline and retains channel, organization, category, verification context, provider source, and contact details. A destination change discards the previous result.

`getCityNews` calls `GET /api/trip-plans/cities/{city}/news?countryCode=...` only when the user presses the news button or refreshes it. It uses the selected GeoNames city and country, URL-encodes both values, and receives one page of article metadata with publisher links. The key and Currents request stay on the backend.

`getDestinationWeather` calls `GET /api/trip-plans/cities/{city}/weather?countryCode=...` only when the user requests or refreshes the forecast. It uses the selected GeoNames destination, URL-encodes the city and country code, and receives local daily dates, conditions, Celsius temperatures, precipitation, wind, and timezone. Open-Meteo is called only by the backend.
`getHistoricalWeather` sends the selected destination, check-in date, and stay length to the backend only after the user requests past weather. The response includes complete daily periods for each comparison year; the client does not call Open-Meteo directly.
