# Attraction recommendations

`AttractionSearchService` exposes a read-only search for places to visit after the user selects a destination city. `AttractionSearchServiceImpl` validates the path city and two-letter country code, reuses the GeoNames-backed `AccommodationCityValidator` to confirm a populated place in geographical Europe, and asks `AttractionSearchProvider` for suggestions. This shared validator is already used by accommodation search and accepts spelling variants through `CityNameNormalizer`. The service preserves provider order and returns at most `ATTRACTION_SEARCH_MAX_RESULTS` (default `10`, allowed `1`–`20`). No attraction is stored in the database.

`SerpApiAttractionSearchProvider` implements the provider with **one** `google_maps` search (`type=search`) for `tourist attractions in City, Country`, using the existing SerpApi key, base URL, and timeout. It reads the first `local_results` page and never follows pagination or place-detail links, so one endpoint request consumes at most one SerpApi search plus one GeoNames validation request. An empty successful search returns `[]`; missing or non-`Success` `search_metadata.status` is an upstream error. Provider error text, raw request URLs, and the API key never reach the client or application logs.

Each result can include a name, category, address, description, rating, review count, coordinates, a Google Maps URL, an image URL, and a website URL. Optional fields are nullable. The provider constructs the Maps URL using Google's documented Maps Search URL with `query_place_id` when a place ID is present, and a name/city/country query as fallback. It only returns HTTPS image and website URLs without embedded credentials or an `api_key` query parameter. Invalid coordinates are omitted.

Google Maps search ranking supplies the recommendation order. SerpApi documents that geographic search results are **not guaranteed** to lie within the requested city, even when location hints are supplied. This endpoint therefore presents recommendations associated with the city query, not verified municipal-boundary membership. A future strict-boundary feature would need city geometry or another authoritative geospatial source.
