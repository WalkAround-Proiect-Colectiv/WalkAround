# Saved trip plans

`SavedTripPlanService` exposes creation and lookup for personal presets and member-scoped creation, listing, lookup, and current-plan selection for group presets. `SavedTripPlanServiceImpl` validates and normalizes the request, creates a `TripPlan` entity, and maps it to `TripPlanResponse`. It never saves flight, bus, or train itineraries, hotel offers, booking links, or prices returned by providers. Transport and accommodation prices must be searched again when a user opens a plan.

## Stored preset

The preset contains a title, optional description, transport mode (`PLANE`, `BUS`, or `TRAIN`), departure and destination city/country pairs, inclusive local departure interval, staying nights, 1 to 9 adults, ticket option, EUR transport budget, and EUR accommodation budget. Missing `adults` defaults to 1. Plane presets also contain an origin airport IATA code; bus and train presets have no airport. The departure city can later be passed to the local city-to-airports lookup when the user wants another airport. It intentionally has no accommodation check-in date: that date depends on the transport itinerary the user eventually selects and is supplied only when searching accommodations.

The service checks departure interval order and the configured maximum calendar-date span for the selected transport. It verifies both country codes against the imported EU member-country table, validates both city/country pairs through GeoNames, and stores the canonical city names. For Plane only, `CityAirportService` confirms the selected origin IATA code appears in the departure city's local airport results. Bus and Train reject an airport value. This validation is for search inputs, not availability: a saved plan may stop producing offers as dates and provider data change.

## Ownership and failure behavior

The controller derives the user ID from the authenticated application JWT. Creation requires that the user still exists; clients cannot supply an owner or group ID in the request body. Personal plans have a user owner and no group. Group plans have a group owner and an optional creator for attribution; the service verifies group membership before creating, listing, or reading them. Personal lookup requires both owner ID and a null group; group lookup requires both group ID and membership. Unknown and inaccessible records return `404`. A plan is created only after all input and GeoNames validation succeeds. GeoNames failure returns a generic `502` without storing a plan.

The first saved group plan becomes current. Later saves add alternatives without replacing the current plan. A group admin can select a different current plan; the service locks the group and clears the old current marker before setting the new one. A partial unique index permits at most one current plan per group. The current marker makes the shared group view explicit about which preset members are discussing. Group members may create alternatives; only admins may change the current selection.

`TripPlanRepository.save` persists the entity in the service transaction. GeoNames validation runs before the group lock and database write, so an external request does not hold the group lock. Create returns `201` with a `Location` header; reads and current selection return `200`. Responses use `Cache-Control: no-store`. Editing and deleting plans are outside this package's current scope.

Flyway V4 creates `trip_plans`; V11 adds the transport mode, renames `flight_budget` to `transport_budget`, and makes the airport conditional. V14 adds the adult count and optional group ownership, creator attribution, and current marker. Existing rows remain personal, one-adult presets. The database requires exactly one of personal owner or group owner. Save requests require both departure fields for every transport.
