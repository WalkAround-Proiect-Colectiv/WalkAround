# Group chat

Each trip group has one conversation, with `conversationId` equal to its group UUID. `GroupChatService` is the controller-facing interface. Every HTTP operation checks current group membership. Chat messages are never accepted over WebSocket.

Polls are chat messages with `messageType=POLL`; their `body` is the question and `options` contains 2 to the configured maximum of distinct labels. V16 adds poll, option, and vote tables. One `(poll_message_id, user_id)` primary key keeps one current choice per user. While a poll is open, choosing another option updates that vote row and publishes one poll update. Repeating the current choice returns the poll without adding another event. A closed poll rejects new votes and changes, but accepts a retry of the same choice. The creator alone can close the poll, and a repeated close is idempotent. Votes and close changes increment the poll revision, update the same message ID, and save a new outbox event in the same transaction. Public Kafka events contain counts and closure state, but omit the voter's selected option; authenticated HTTP reads include only the current viewer's selected option.

Message sequence numbers identify chat bubbles and never change. `eventSequence` orders both new messages and poll updates within the conversation. The outbox has an event UUID primary key so a poll can have multiple update events. The client obtains an event cursor before its initial message page, subscribes before reading, and requests events after that cursor to cover races. Reconnect and periodic catch-up use `GET /events?afterEventSequence=...`. Each event returns the current state of its message; the client merges by message ID and poll revision. Kafka records use the conversation ID as their partition key and the realtime service deduplicates by event sequence.

`POST /api/trip-plan-groups/{groupId}/chat/messages` takes a client-generated UUID `messageId` and a text body. The service trims and validates text, then saves the message and an outbox row in one database transaction. `JdbcGroupChatRepository` locks the conversation row before allocating its next sequence, so concurrent writers get unique, increasing per-conversation numbers. A retry with the same ID, sender, group, and body returns the existing message without allocating another sequence or outbox row. Reusing the ID with different content returns `409`.

The paged `GET /messages` returns the newest page when no cursor is supplied, messages after `afterSequence` in ascending order for catch-up, or earlier messages before `beforeSequence`. Each page is sorted by sequence. A sender's current display name is joined from `users`; deleted senders are shown as Former member. The API never trusts a client-supplied sender ID.

The `GET /socket-ticket` endpoint verifies membership and signs a short-lived JWT containing `token_use=group_chat`, the user ID, and the conversation ID. The realtime service validates this token before accepting a WebSocket subscription. Its issuer, audience, and signing secret are shared with the application login configuration.

`KafkaGroupChatOutboxRelay` polls pending outbox rows with `FOR UPDATE SKIP LOCKED`. Only the earliest unpublished event per conversation is eligible, preserving order even with multiple relay workers. It sends Kafka records keyed by conversation ID, waits for broker acknowledgement, and marks rows published in the same database transaction. Failed sends are deferred with bounded backoff. A crash after broker acknowledgement but before the database commit can republish a record: Kafka delivery is at least once, while clients deduplicate by event sequence and merge by `messageId` and poll revision. This is the practical meaning of one visible message or poll update per save; the outbox cannot guarantee exactly one Kafka record across a database and broker crash boundary. [Transactional outbox reference](https://microservices.io/patterns/data/transactional-outbox.html).

The relay selects one eligible event at a time and repeats up to its configured batch size in one poll. This lets a burst of votes for the same poll move through Kafka without waiting for a full poll interval between each vote, while the outbox query still blocks later events for that conversation until earlier events are acknowledged.

The relay logs a message ID, conversation ID, and sequence after a broker acknowledgement. If connected clients do not see an update, compare that entry with the realtime service's received-event log for the same conversation and sequence. Logs never include chat bodies.

`GROUP_CHAT_TOPIC` defaults to `trip-group-chat-topic` with six partitions. Keep the topic's partition count fixed after messages have been published; changing it can remap a conversation key to a different partition. The Application API creates the topic on startup. Page size, poll interval, batch size, publish timeout, maximum retry delay, message length, and ticket lifetime are application settings.
