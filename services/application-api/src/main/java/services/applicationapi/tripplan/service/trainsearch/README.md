# Train search

`TrainSearchService` is the controller-facing interface for `POST /api/trip-plans/train-searches`. `TrainSearchServiceImpl` validates both city/country pairs using GeoNames and the EU country repository. It searches Omio for every supported route and also searches Bilo for `TWO_ONE_WAY` requests when both validated countries are Romania and `BILO_API_KEY` is configured. The local airport table is not used. Each source contributes up to `trainSearchMaxResults` (default 3), so a domestic two-one-way response can contain up to six offers, sorted by estimated EUR total. An unavailable source does not hide successful results from the other source.

`RomaniaTrainSearchService` is the provider-independent contract for Romania-specific train results. `TrainSearchServiceImpl` checks whether that service supports the requested ticket option before calling it. The current implementation is `BiloTrainSearchServiceImpl`; a different Romanian source can implement the same contract without changing the main train search flow.

The request accepts a local departure datetime interval, 1 to 365 staying nights, total EUR budget, 1 to 9 adults, and `ROUND_TRIP` or `TWO_ONE_WAY`. Missing `adults` defaults to 1. Bean Validation checks field presence and shape. The service limits departure dates to the next 364 days and to `trainSearchMaxDateRangeDays` (default 7). The provider sends `travel_mode=train`, `currency=EUR`, `sort=price`, the selected adult count, and up to 100 offers per page. The same count is used for outbound and reverse searches. It retains bookable train-mode offers with a parseable local arrival and departure. Budget filtering is done locally because Omio Search has no budget parameter.

For `ROUND_TRIP`, outbound dates are searched with return dates from outbound date + nights through that date + `trainSearchMaxArrivalOffsetDays` (default 2). Only results whose actual outbound arrival date + nights matches the searched return date survive. The cheapest outbound candidates are followed by at most `trainSearchMaxResults` trip-detail requests; the return option's `round_trip_price` is the combined fare. For `TWO_ONE_WAY`, outbound and reverse-direction searches are paired; return date is actual outbound arrival date + nights. Reverse searches for the same date are reused. Results are the cheapest among explored pages and candidates, not a global fare guarantee.

`trainSearchMaxPagesPerDate` defaults to 1. With defaults, round trip can make up to 21 searches, 3 detail requests, and 2 city lookups. After selecting at most three itineraries, transfer stop IDs are resolved through Omio Places once per distinct ID for that request. This adds provider requests when transfers are present. A failed stop lookup does not discard a priced itinerary; the response retains its ID and hides missing location details on the frontend. There are no automatic retries. Upstream failures yield a generic 502 without upstream text or the API key.

Responses contain both journeys, station and city names, dates and times, carrier and optional validated Omio logo, duration, changes, legs, transfer stops and optional availability. The frontend displays operator details and separate return information. Omio links are prefilled route/date searches, not exact fare or booking links; users must reselect the offer and price can change.

`BiloTrainProvider` isolates the HTTP integration at `POST /search`; `BiloHttpTrainProvider` sends a bearer key server-side, requests the selected count in `passengers`, rail mode, second class, price sorting, and at most `biloSearchPageSize` results per day (default 50). It reads only priced rail journeys and preserves Bilo's estimated-fare flag, partial-catalog flag, and published HTTPS ticket/search links. `BiloTrainSearchServiceImpl` pairs outbound journeys in the requested departure window with reverse journeys departing on outbound arrival date plus staying nights, using the same passenger count in both directions. Bilo does not offer a round-trip fare in this search contract, so it is queried only for `TWO_ONE_WAY` requests. Return-day searches are cached within the request. Published schedules and fares do not confirm seat availability.

Bilo runs before Omio for eligible Romanian two-one-way routes so its request is not delayed by Omio's date-by-date searches. It receives the validated user-selected city names unchanged, rather than GeoNames' returned display names. The service logs whether both cities are in Romania, the selected ticket option, and whether the Romania provider supports the request, without logging credentials.

Each eligible Bilo search fetches the latest RON-to-EUR rate once from Frankfurter's `/v2/rate/ron/eur` endpoint. RON totals are multiplied by that rate for EUR budget comparison; the response keeps the original RON total and marks the EUR display as approximate. A failed or invalid rate lookup makes Bilo unavailable for that request, while Omio can still return results. Each source is capped separately to ensure Bilo offers remain visible beside Omio offers. No Bilo API key means only Omio is queried.

To activate Bilo, put a developer-dashboard bearer key in `BILO_API_KEY` in the local `services/application-api/.env`, ensure the IDE run configuration exports that file to the Spring Boot process, and restart application-api. Spring Boot does not automatically read `.env` files. The service logs at debug level when the Romania provider does not support the selected ticket option. The key is never returned to clients or logged. Bilo can return schedules without a fare; those journeys cannot pass a budget filter and are omitted. A configured key still requires an active Bilo account and accepted terms.
