# Bus search

`BusSearchService` is the controller-facing interface. `BusSearchServiceImpl` validates both GeoNames cities and EU country codes, resolves them to Omio location IDs through `BusSearchProvider`, assembles tickets, filters the **combined EUR price** against the user's budget, sorts by total price, and returns at most `busSearchMaxResults` (default 3). `ScrappaOmioBusSearchProvider` is the only class aware of Scrappa's HTTP and JSON format. A new provider can implement the interface without changing the controller or service.

The request uses the same departure interval, stay length, adult count, and ticket options as flight search. Missing `adults` defaults to 1; validation accepts 1 to 9, matching Omio Search. The provider requests `travel_mode=bus`, `currency=EUR`, `sort=price`, the selected adult count, and up to 100 results per page. The same count is used for outbound and reverse searches. It accepts bookable bus-mode trips with parseable local departure and arrival times. `amount_minor` is converted from euro cents. The exact local departure interval and total group budget are enforced in this service because the upstream search has no budget filter.

For `ROUND_TRIP`, each outbound date is searched with return dates from outbound date + nights through that date + `busSearchMaxArrivalOffsetDays` (default 2). Only outbounds whose actual arrival date + nights equals the searched return date survive. The cheapest candidates are followed by at most `busSearchMaxResults` trip-detail calls; their `round_trip_price` is the combined fare. For `TWO_ONE_WAY`, outbound and reverse-direction one-way searches are combined. Return dates come from the actual outbound arrival date + nights, and return searches for the same date are reused. Results are the cheapest among explored pages and candidates, not a global price guarantee.

Different return journeys remain separate options. The collapsed frontend card shows the return departure so these offers can be distinguished without opening each card.

Search volume is bounded by `busSearchMaxDateRangeDays` (default 7), `busSearchMaxArrivalOffsetDays` (default 2), and `busSearchMaxPagesPerDate` (default 1). With defaults, round trip can make up to 21 search calls, 3 detail calls, and 2 city-place calls. After choosing at most three results, the service resolves each distinct transfer position ID with `GET /api/omio/places?id=...` once per user request. This adds one provider request per distinct transfer stop; a failed resolution retains the itinerary with the position ID and null stop details. Scrappa documents one credit per Omio request. There are no automatic retries. Upstream search failures become a generic 502 response; the API key and upstream error text are never returned to the client.

The Places adapter searches the returned place, result, results and child nodes for the **requested** position ID. It does not assume the requested station is a top-level result. If a lookup returns no matching ID or omits a usable name/city, it logs the position ID without logging the provider payload or API key. The frontend hides unresolved IDs and displays the transfer type and duration when available.

The response contains outbound and return stations, cities, country codes, times, carrier name, an optional validated Omio logo URL, duration, change count, optional tickets-left and split-ticket indicators, legs with duration and time zones, transfer type and wait duration, resolved transfer stop IDs, names, cities and country codes, ticket option, and total EUR price. Missing upstream fields remain null or empty. The adapter accepts logo URLs only from `https://static.omio.design`; the frontend uses a generic bus icon otherwise. It does not expose fare-class or original-price fields because those can be incomplete or misleading beside a combined itinerary price. Scrappa's search response does not provide a booking URL for the exact offer. The frontend labels its Omio link as a new search, not a direct booking link.
